# 05 — Per-instance Dynamic Flags & Sharing Detection

Two related features:

1. **Per-instance flags** — a `per_team` container challenge can mint a **unique flag per
   team instance**, so two teams solving "the same" challenge submit different flags.
2. **Sharing detection foundation** — because flags now identify a team, the platform can
   notice when team B submits team A's flag and raise a **sharing signal** (log + metric).
   Detection only in v0.2; no automated action.

Both are opt-in (`challenges.flag_mode = per_instance`) and only valid for `container`
challenges. `static` challenges are byte-for-byte v0.1.

## Flag generation

New helper package `api/internal/flags` (or a small type in `scheduler`):

```go
type Generator struct{ prefix string } // OSCTF_FLAG_PREFIX, default "osctf"

// New mints a unique flag for a (challenge, team) instance.
func (g *Generator) New() (string, error) {
    var b [24]byte
    if _, err := rand.Read(b[:]); err != nil { return "", err }  // crypto/rand
    return fmt.Sprintf("%s{%s}", g.prefix, base32Crockford(b[:])), nil
}
```

- `crypto/rand`, ≥ 128 bits of entropy (24 bytes → 39 Crockford base32 chars). Guessing or
  colliding is infeasible; no uniqueness retry loop is needed, but the `instances.flag`
  write is guarded anyway (below).
- Format `osctf{…}` matches the house style so participants can't tell dynamic from static
  by shape. The prefix is configurable to match an event's brand.
- The flag is generated by the **scheduler** at Start (before deploy), stored on the
  instance row, then injected. It is a **secret** from birth — see the non-negotiables.

## Storage & injection

- **Storage:** `instances.flag` (added in [`02-database.md`](02-database.md)). Written in the
  same `DeployForTeam` row-insert that allocates the port, *before* `rt.Deploy`. If the
  insert loses the `uq_instances_per_team` race, the winner's existing flag is used
  (idempotent Start — never two flags for one instance).
- **Injection:** the Manager sets `spec.Env["FLAG"] = instances.flag` (else `challenges.flag`
  for static). The runtime injects `FLAG` exactly as in v0.1 — the container reads it and
  serves it to whoever solves the challenge inside that container. The runtime is oblivious
  to flag *mode*.

## Submission validation (the changed hot path)

v0.1 compares against `challenges.flag` inside the locked transaction
([`submissions/service.go:112`](../../api/internal/submissions/service.go#L112)). v0.2 makes
the *comparison target* flag-mode-aware, inside the same transaction and solve/attempt
rules:

```
in the locked tx, after solved/attempt checks:
  if ch.flag_mode == 'static':
      correct = compareFlag(provided, locked.Flag, ci)              // v0.1, unchanged
  else: // per_instance
      inst = GetTeamInstance(ch.id, team)                           // the submitter's own instance
      if inst == nil OR inst.flag == "":
          return 403 no-instance ("start the challenge first")
      correct = compareFlag(provided, inst.flag, ci)
      if !correct:
          owner = FindInstanceByFlag(ch.id, provided)               // a DIFFERENT team's instance?
          if owner != nil && owner.team_id != team:
              sharingSignal(team, owner.team_id, ch.id, submissionID)
  // record the submission exactly as v0.1 (provided verbatim, correct bool, ip)
```

Key points:

- **Constant-time compare is unchanged** (`compareFlag`, `crypto/subtle`). Per-instance
  flags reuse it against the team's own `inst.flag`.
- **A team solves only with its own flag.** Submitting the *correct string* that happens to
  be another team's flag is `correct=false` for the submitter — it never credits a solve
  (success criterion #1). The unique per-team solve index is unchanged.
- **No-instance guard.** Submitting a per-instance challenge with no running instance is a
  `403` telling the user to start it — not a silent wrong answer, because there is nothing
  legitimate to compare against.
- **The comparison and the sharing lookup are inside the same locked transaction** as the
  v0.1 solve/attempt logic, so counts and signals are consistent.

## Sharing signal

```
sharingSignal(submitter, owner, challenge, submissionID):
  audit.Record(action="flag.shared", actor=submitter_user,
               subject_type="team", subject_id=submitter_team,
               meta={challenge, owner_team, submission})   // NEVER the flag value
  metrics.flagSharingSignals.Inc()
```

- **Detection only.** No auto-ban, no auto-zero, no auto-hide. Organizers see the signal in
  the admin submission/audit log and decide ([`00-overview.md`](00-overview.md) scope-OUT).
- **Never reveal to the submitter.** The response is an ordinary "incorrect flag"; leaking
  "that's team X's flag" would help cheaters triangulate. Same generic error as any wrong
  flag.
- **Meta carries team ids, never the flag.** The audit `meta` and every log line omit the
  flag string (non-negotiable below). The owning team is identified by id.
- **What it does and doesn't prove.** A signal means the exact bytes of another team's
  instance flag were submitted — strong evidence of sharing, but organizers judge (a team
  could be framed by a leaked flag). v0.2 surfaces; it does not adjudicate.

## Non-negotiables (flags are secrets)

1. `instances.flag` and `challenges.flag` are **never** serialized in any participant or
   admin API response. The admin Instances page shows state/port/owner/expiry — **not the
   flag**.
2. Flags are **never** written to logs, `audit_log.meta`, metrics labels, or error
   messages. `sharingSignal` meta holds ids only.
3. The only place a flag leaves the database is `spec.Env["FLAG"]` → inside the challenge
   container. (And the operator's `challenge.yaml` for static flags, as in v0.1.)
4. `FindInstanceByFlag` exists solely to map a submitted string to an owning team id for the
   signal; its row (a secret) is used for the id and discarded.

## Backwards compatibility

- Default `flag_mode='static'` → every v0.1 challenge is unchanged; the submission path
  takes the identical branch and compares against `challenges.flag`.
- `per_instance` requires `kind='container'` (DB constraint) — a standard challenge cannot
  accidentally opt in.
- The e2e/smoke static-flag flows pass untouched.

## Decision log

- **Crockford base32, 128-bit, `osctf{…}` shape.** Indistinguishable from static flags,
  infeasible to guess/collide, human-legible if pasted.
- **No-instance submit is `403`, not wrong-answer.** Avoids burning an attempt on a
  configuration state the user can fix, and is clearer.
- **Signal on the *exact-match-to-another-team* case only.** Fuzzy/substring matching would
  produce false positives and is a v0.3+ anti-cheat concern; v0.2's foundation is the exact
  flag-ownership map.
- **Store the flag on the instance row, not Redis.** It shares the instance's lifecycle
  exactly (born at allocate, gone at destroy) and inherits the row's access controls.
